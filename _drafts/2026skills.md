一月時寫了[器靈與技能魔石 - 我如何看待 AI (2026)](life/2026-how-i-treat-ai)，談了「技能魔石（Agent Skill）」為什麼是今年的重點。但其實到了年底，Harness 已經進一步接過了撰寫 Agent Skill 的工作。諸如 Hermes Agent 等可以自行總結使用者的操作，需要時也會撰寫 Skill，已經完全可以從外派幫手變成能了解你，可以一起工作的夥伴。

這篇來談實際怎麼使用 Skill：怎麼裝別人的技能、怎麼把自己累積的經驗變成技能、怎麼讓多個 Agent 協同工作。

## 寫技能：把經驗「祭煉」成可複用的東西

這年最大的轉變是：**以前會寫 bash 腳本的工作，現在改寫成 skill 或 note**。

我目前在用的幾個技能：

- **todomd**：我的待辦清單格式與處理規則（含 recurrent tasks 流程），放在 logseq 的 TODO 頁，Agent 讀完就能照著格式新增、勾選。
- **changelog**：從專案的 commit 產出 changelog。
- **bobee-post**：用 Antigravity 產出 [bobee.tw](http://bobee.tw) 的貼文與附圖。

這些技能的共同特色是：一個資料夾、一個 README（或 SKILL.md）、明確的適用場景。Agent 讀完就知道什麼時候該用、怎麼用。

寫技能跟寫腳本的差別在於：技能是**給 Agent 看的操作手冊**，所以重點不在指令本身，而在「什麼時候用、判斷標準是什麼、例外狀況怎麼處理」。bobee-post 就是典型例子——貼文格式很容易寫成腳本，但「語感」只能寫成規則讓模型去遵循。

## 裝技能：一行命令

除了自己寫之外，也能複用別人分享的命令。
現在分發技能最常見的方式是透過 vercel-labs 的 skills CLI：

```sh
npx skills add [repo]
```

這讓「學一個新技能」從複製一段 prompt 變成安裝一個 package。
Skill 很容易分享，而且幾乎能處理所有軟體能做到的事情。這同時出現了很高的信任風險：。

## 多 Agent 協作：像管遠端團隊一樣

2026 年我的日常工作流大致長這樣：

1. 主 Agent（pi 或 hermes agent）讀我的專案 AGENT.md 與 TODO
2. 它根據任務決定要載入哪些 skill
3. 需要時 spawn 子 Agent 分頭處理（如同時 build desktop 與 mobile）
4. 每個 Agent 的產出寫回檔案（todomd、changelog、summary），而不是留在對話裡

有兩點心得：

**把 Agent 當真人同事看。** 它們跟真人一樣會「接到模糊需求就自由發揮」，所以任務要寫清楚验收條件；但跟真人不同，它們智力一致、共享同一套知識庫，可以隨時複製一份新的。分工方式我分成四類：無腦分工（聽指令不溝通）、分棒交接（寫清楚工作日誌給下一棒）、流水線（依序執行、簡化交接文件）、平行分頭探索（主 Agent 分析後產生子 Agent 同時探索不同面向）。

**每多一種 AI，就像多一個新同事。** 跟 AI 協作的心法跟跟遠端同事共事一樣：清楚的需求、明確的驗收、定期的複盤。

## 還缺什麼

目前這些強大代理（Claude Code、Antigravity、pi）多半是 CLI。要推廣到大眾，還缺一個更直覺的界面——如 Hermes Agent 提供桌面端，安裝時會自動跑各種腳本，安裝後也有方便的介面可以作管理；「豆包手機」預覽版內建在手機系統中、能讀取畫面並跨 App 操作的模式，可能是接下來幾年普及的方向。

另一塊是本地化。線上 Agent 一旦無法運作，對依賴它們的專業工作者打擊極大（上一篇有談過）。這半年我跑過 LM Studio + 本地模型來搭配 pi，或者 olmx + 本地模型來搭配 Hermes Agent，這些組合在離線時至少能維持最基本的對話與程式輔助。本地 LLM 在 2026 年底的水準已加強很多，雖還不足以完全替代線上 LLM，但「有備援」與「沒備援」的差異，比我預期的大。

## 結語

在 2026 年的今天，與其說我們是在「使用 AI 工具」，不如說我們是在「與 AI 團隊協作」。如何定義目標、評估結果、調度合適的 Agent，將成為這個時代最核心的競爭力。
